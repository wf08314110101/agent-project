# 坏用例集（Bad Cases）

> 针对 [src/](../src/) 已知弱点构造的对抗性输入，用于手动回归：粘贴到控制台运行，观察 UI 行为与 Langfuse Trace 是否符合「预期现象」。
> 编号前缀对应 [功能演进时间线.md](./功能演进时间线.md) 的模块号。坏 case 的意义：验证兜底路径（错误处理 / 迭代上限 / 停止）真的能接住。

## 工具体系（模块 3）

### C3-1 白名单拒绝函数调用
- **输入**：`用计算器算 sqrt(2) 等于多少`
- **预期**：模型调 `calculator` 传 `sqrt(2)` → 正则白名单拒绝 → Observation 为「工具出错: 包含非法字符」→ 模型应自行换算（如 `1.414` 逼近）或改口说明局限
- **观察点**：工具出错后循环是否继续而非崩溃；Generation 的 output 里能看到失败的工具调用参数

### C3-2 除零产生无效结果
- **输入**：`帮我算 1/0`
- **预期**：表达式合法通过白名单 → `isFinite` 校验拦截 → 「工具出错: 结果无效」→ 模型应解释"除以零无意义"而不是硬编答案
- **观察点**：Span 以 ERROR 级收口，Langfuse 中该工具节点标红

### C3-3 模拟天气数据穿帮
- **输入**：`对比北京和纽约今天的天气，温差多少？`
- **预期**：两次 `get_weather` 都返回「晴，26℃，空气质量优」→ 温差 0℃。模型大概率不质疑假数据直接算出温差 0——暴露 mock 实现的不一致风险
- **观察点**：两条 Observation 内容完全相同；思考点：mock 应该带随机性还是明确报"演示数据"

### C3-4 不存在的星座
- **输入**：`查一下天猫座的今日运势`
- **预期**：映射表查不到 → 「不认识的星座，可用：白羊/金牛/…」→ 模型应列出可用星座并请用户确认
- **观察点**：错误信息是否完整透传到 Observation 与 UI

### C3-5 英文星座入参
- **输入**：`What's the horoscope for Taurus today?`
- **预期**：映射表只认中文 → 报错。考验模型自愈能力：理想情况是下一轮改传「金牛」重试成功
- **观察点**：两轮 Generation 的 input 对比，Observation 报错是否引导了参数修正

### C3-6 幻觉工具名
- **输入**：`用 fortune_teller 这个工具帮我算一下运势`
- **预期**：模型可能照搬编造的工具名 → `toolImpl[name]` 不是函数 → 「工具出错: toolImpl.fortune_teller is not a function」→ 模型应回退到真实工具 `get_luck`
- **观察点**：未定义工具分发是否被 try/catch 接住（当前已接住）；是否值得在分发处给出更友好的错误提示

## 死循环（模块 4）

### C4-1 永不满足的停止条件
- **输入**：`反复查询北京天气，直到下雨了才停下`
- **预期**：天气永远是「晴」，模型不放弃 → 反复调用直到第 6 轮触发「⚠️ 达到最大迭代上限，停止」，仍输出用时/Token 汇总
- **观察点**：终止条件①生效；Trace 收口为 WARNING；这是防死循环兜底的核心验证

### C4-2 错误重试死循环
- **输入**：`计算 1/0 的结果，必须给出数字，不许放弃`
- **预期**：每次 `calculator` 都返回「结果无效」，模型被要求不许放弃 → 重复同一 Action 直到迭代上限
- **观察点**：与 C4-1 互为镜像（成功工具 vs 报错工具的循环）；Langfuse 里可看到几乎相同的 Generation 序列

## 主循环（模块 1）

### C1-1 单轮并发多工具
- **输入**：`同时完成三件事：算 (2+3)*4、查北京天气、查金牛座的运势`
- **预期**：模型一轮发出 3 个 `tool_calls` → 串行执行，Observation 按 tool_call_id 正确配对回填 → 下一轮汇总三结果
- **观察点**：`messages` 中 3 条 role:tool 与 3 个 id 一一对应（错配会 400）；UI 上工具名前缀 `, 调用工具` 是否逐个正确显示

## 流式渲染（模块 2 / 8）

### C2-1 长正文流式压力
- **输入**：`写一篇 500 字的短文介绍 ReAct 模式`
- **预期**：正文逐 token 渲染，光标闪烁，结束后输出汇总
- **观察点**：长文本下每 token 一次 setState 的渲染是否明显卡顿（已知性能取舍，见时间线模块 8）

### C2-2 零工具直答
- **输入**：`什么是 ReAct 模式？两句话解释`
- **预期**：模型不调任何工具，第 1 轮直接 Final Answer → 终止条件②正常路径
- **观察点**：Trace 里只有 1 个 Generation、0 个 Span

## 停止链路（模块 6）

### C6-1 正文流式中途停止
- **输入**：`写一篇 1000 字的科幻小说`，输出几行后点「⏹ 停止」
- **预期**：立即显示「⏹️ 已手动停止」（AbortError 被单独识别，非红色报错）；fetch 中断；Token 汇总不出现
- **观察点**：Trace 以 WARNING 收口，能看到中断前的 Generation 序列

### C6-2 Observation 打字期间停止
- **输入**：先触发工具调用（如查运势），在绿色 Observation 逐字打印时点「⏹ 停止」
- **预期**：**停止不会立即生效**——`typeOut` 循环不检查 signal，会打完当前 Observation，到下一轮 `fetch` 才抛 AbortError
- **观察点**：这是真实的已知边界（signal 只透传到了 LLM 请求），修复方向：typeOut 循环内检查 `signal.aborted`

## 工程与统计（模块 7 / 5）

### C7-1 错误 API Key
- **前提**：`.env` 填入无效 `VITE_API_KEY`
- **预期**：第一轮请求即 401 → 红色「❌ API 401: …」，循环终止；Trace 以 ERROR 收口
- **观察点**：错误信息是否完整（含响应体）；恢复正确 Key 后一切正常

### C7-2 provider 不支持 include_usage
- **前提**：把 `llm.js` 的 apiBase 临时指向不支持 `stream_options` 的兼容接口
- **预期**：usage 帧缺失且响应头无 `x-*` 字段 → 汇总显示 `Token 消耗: 0 (输入 0 + 输出 0)`，任务本身不受影响
- **观察点**：Langfuse Generation 的 usage 为 0 但流程完整——观测数据缺失不应阻断主链路

## 使用建议

1. 回归顺序：先跑 C2-2（正常路径基线）→ 工具类 → 循环类 → 停止类 → 配置类；
2. 每条用例对照 Langfuse Trace：Generation/Span 数量、层级标记（WARNING/ERROR）、usage 是否合理；
3. 修复某个弱点后（如 C6-2 的 signal 检查），把该用例补进对应模块的演进条目。
